# Requirements: Android Device Smoke-Test Defects

**Status:** Requirements discovery (2026-09-16). Not yet designed.
**Context:** First Android build installed on a physical device. App runs. Two defects found. Parent milestone: `google-play-first-release-requirements.md` Phase 1.
**Goal:** Both defects fixed and re-verified on device before the first AAB upload. Zero iOS behavior change.

## 1. Bedrock facts (verified against the repo, 2026-09-16)

### Defect 1 — no launcher icon
- `app.json` → `android.adaptiveIcon.foregroundImage` = `./assets/adaptive-icon.png`, background `#f9f9fb`.
- `assets/adaptive-icon.png` is the **Expo blank-template placeholder** (grey concentric circles on white, 1024×1024, dated 1 Apr). It is byte-identical (md5 `97dae5a0…`) to `assets/splash-icon1.png`. It has never been replaced with the parkDaddy mark.
- Rendered on a near-white adaptive background, the placeholder reads as "no icon".
- Real brand mark exists: `assets/icon.png` (1024×1024 RGBA, navy field, green "P" + gold meter) and `assets/parkDaddyIcon-nobackground.png` (2048×2048, transparent).
- `android/` is gitignored and regenerated by prebuild/EAS from `app.json`, so the fix lives in assets + `app.json` only. The generated `mipmap-*/ic_launcher_foreground.webp` files are derived from the placeholder.
- The notification icon also uses `./assets/icon.png` (full-colour). Android renders notification icons as alpha-only silhouettes; a full-colour RGBA icon becomes a solid blob. Out of scope for this defect but adjacent — flag for parent checklist FR-4.

### Defect 2 — Google SSO detour: "page not found" → splash → signed in
- `src/components/GoogleSignInButton.tsx:24` passes `redirectUrl: Linking.createURL("oauth_callback")` → resolves to `parkdaddy://oauth_callback` in production builds.
- **No route named `oauth_callback` exists** under `app/`. There is also no `app/+not-found.tsx`, so Expo Router shows its default "Unmatched Route" screen for any unknown deep link. This is the "page not found".
- Why iOS never showed it: iOS uses `ASWebAuthenticationSession`, which captures the redirect URL inside the auth session and hands it to the JS promise **without** delivering it to the app as a deep link. Android uses a Chrome Custom Tab; the redirect is delivered as a real `VIEW` intent to `MainActivity`, so Expo Router *also* navigates to it. Same code, different OS plumbing.
- `AndroidManifest.xml` intent filter for scheme `parkdaddy` is present and correct (`launchMode="singleTask"`), so the deep link reaches the existing activity when the process is alive.
- `AnimatedSplash` is a one-way latch: once `stage === "gone"` it returns `null` and never re-mounts on `appReady` changes. Therefore the splash reappearing means the **JS runtime restarted** (process killed or activity recreated while the Custom Tab was in front), not a readiness flicker.
- After a restart, `startSSOFlow`'s promise is gone, so `setActive` + `router.replace("/(tabs)")` in the button never run. Sign-in still completes because Clerk's token cache / client reload finds the session and the `(auth)/_layout.tsx` and `(tabs)/_layout.tsx` `Redirect` guards route the user in. This explains "eventually logs in".
- Google SSO **worked** with no Android OAuth client in Google Cloud. Parent spec FR-2 assumed one was required; that assumption is wrong for Clerk's web-based `oauth_google` strategy. Strike it.
- The Apple sign-in button uses the identical `redirectUrl` pattern (`AppleSignInButton.tsx:22`); it is slated to be hidden on Android per the parent spec, so no separate fix needed there.

## 2. Functional requirements

- **FR-1 Launcher icon shows the parkDaddy mark** on the Android home screen, app drawer, recents, and settings app list, at every density, in both circular and squircle masks.
- **FR-2 Adaptive icon respects safe zone.** Foreground artwork must sit inside the 66% centre safe zone of the 108dp canvas so no mask clips the "P" or meter. Background colour must match the mark's navy field so the mask edge is invisible.
- **FR-3 Monochrome/themed icon (Android 13+)** — provide a `monochromeImage` or explicitly decide to skip. Decision: skip for first release unless trivial; note as follow-up.
- **FR-4 Google SSO redirect lands on a real route.** After the Custom Tab closes, the user must never see the "Unmatched Route" screen. The redirect target must be a route that either renders nothing or renders the sign-in screen.
- **FR-5 Warm-path SSO completes in-app.** When the process survives the Custom Tab, the flow must end with `setActive` → tabs, with no intermediate screen flash.
- **FR-6 Cold-path SSO must sign the user in deterministically.** Diagnostic run 2026-09-16 (see §7) proves the **process is dead** when the redirect arrives: Android logs `Start proc … for next-top-activity {MainActivity}`, then `Running "main"` (fresh JS). The cold path is the *only* path on this device, every attempt.
  - FR-6a: The cold path currently signs the user in by accident, not by design. `@clerk/clerk-expo` 2.19.33 `useSSO` completes native sign-in only *inside* the `startSSOFlow` promise: after `openAuthSessionAsync` resolves it reads `rotating_token_nonce` from the redirect URL and calls `signIn.reload({ rotatingTokenNonce })`. There is no `getInitialURL` handling anywhere in the package. When the process dies, that code never runs. The observed "eventually logs in" comes from Clerk reloading its client from SecureStore on boot and finding the session already attached server-side. This must be **verified** in design (does the session exist on the native client without the nonce reload, or is it a race?) — never assumed. See [[feedback_audit_design_risks]].
  - FR-6b: The app must handle a cold start whose launch intent is the SSO redirect URL: read the initial URL, complete the Clerk sign-in explicitly (nonce reload or equivalent), then route to tabs. Result: splash → tabs, no error-looking screen, no reliance on the accidental path.
  - FR-6c: Root-cause the kill so warm path (FR-5) is possible on normal devices. One more capture needed, see §7 follow-up. Even if the cause is the test device, FR-6b stays: real users' phones will kill the app behind Chrome some of the time.
- **FR-8 No unknown deep link ever shows an error-looking screen.** Generalisation of the user's constraint: any URL the app receives that does not match a route must render a neutral, branded, non-alarming state (same navy as the splash, optional spinner, no words like "not found", "error", "unmatched"). This covers the SSO callback today and any future mis-typed notification route or stale link.
- **FR-7 Cancel path is clean.** Backing out of the Custom Tab returns to the sign-in screen with the button re-enabled and no navigation side effect.

## 3. Non-functional requirements

- **NFR-1 iOS unchanged.** `assets/icon.png` and the iOS auth flow must produce identical results to the shipped build 18. Never break userspace.
- **NFR-2 Fix is config/asset-level where possible.** No generated `android/` edits (folder is gitignored and rebuilt by EAS).
- **NFR-3 Diagnosable.** The SSO fix must include a way to tell warm path from cold path on device (log line or Sentry breadcrumb) so the next smoke test can confirm which path ran.

## 4. Acceptance criteria

1. Fresh internal-distribution Android build shows the parkDaddy icon in launcher, drawer, recents. Screenshot captured for the Play listing checklist.
2. Google SSO on device: tap → Custom Tab → return → tabs. No "Unmatched Route" screen at any point, on at least 3 consecutive attempts.
3. Cold path: FR-6a evidence captured and recorded in this doc; result of an SSO attempt after the fix is splash → tabs, signed in, no error-looking screen. If the restart was app-caused, SSO no longer restarts (warm path).
4. Cancel the Custom Tab: back on sign-in, button enabled.
4b. Send the app a bogus deep link (`adb shell am start -a android.intent.action.VIEW -d "parkdaddy://definitely-not-a-route"`): neutral branded screen, no error text (FR-8).
5. iOS build from the same commit: icon and SSO behaviour unchanged (spot-check on simulator or device).
6. Parent spec FR-2 (Android OAuth client) struck through with a note referencing this doc.

## 5. Decisions (answered 2026-09-16)

1. **Icon source of truth: `assets/parkDaddyIcon-nobackground.png`** as the transparent adaptive foreground over a solid navy background colour sampled from `assets/icon.png`'s field. Correct adaptive construction; the "P" + meter must be scaled into the 66% safe zone (design phase decides exact padding).
2. **Cold path frequency: every attempt.** Elevates FR-6 from accept-and-document to investigate-then-fix. See FR-6a diagnostic.
3. **Redirect target: no preference**, hard constraint only — the user must never see "page not found" or any text that reads as a bug or failure. Captured as FR-8. Design phase picks the mechanism (dedicated callback route, existing route, custom not-found screen, or a combination).

## 5b. Remaining open items

- **Kill reason** (FR-6c). The first capture filtered out the kill line. One more run during SSO:
  ```
  adb logcat -s ActivityManager:I | grep -i parkdaddy
  ```
  Look for a `Killing <pid>:com.parkdaddy.app … : <reason>` or `Process com.parkdaddy.app … has died` line *before* the `Start proc`. Reason strings such as `empty`, `cached`, `bg-anr`, `excessive cpu`, or an OEM-specific tag decide whether it is device policy or app fault. Also check on the device: Developer options → **Background process limit** must be "Standard limit", and report device model + RAM (`adb shell getprop ro.product.model; adb shell head -1 /proc/meminfo`).
- **Which build was tested?** Dev client (`expo run:android`), EAS `preview` APK, or `production`? Affects only the diagnosis, not the requirements.
- Exact navy hex for the adaptive background (sample from `icon.png`; verify against `src/theme` colours so launcher and splash `#0f172a` do not visibly clash).

## 7. Diagnostic log

**2026-09-16, first SSO attempt with logcat attached.** Command: `adb logcat -s ActivityManager:I ReactNativeJS:V | grep -Ei "start proc.*parkdaddy|died|running \"main\""`. Output, verbatim:
```
09-16 19:36:25.982  1641  1741 I ActivityManager: Start proc 13440:com.parkdaddy.app/u0a47 for next-top-activity {com.parkdaddy.app/com.parkdaddy.app.MainActivity}
09-16 19:36:26.180 13440 13464 I ReactNativeJS: Running "main"
```
Reading: only one `Start proc`, and its reason is `next-top-activity` (Android resuming an activity whose process is gone), not `top-activity`/`activity` (launcher start). So the app was running, went behind the Custom Tab, was killed, and was re-spawned by the redirect intent. JS re-ran from scratch 200 ms later, which is the splash the user sees. Screenshot after boot shows Expo Router's default "Unmatched Route — Page could not be found — parkdaddy://oauth_callback" with "Go back • Sitemap" links: the launch intent's URL became the initial route.
