# Requirements: parkDaddy First Google Play Release

**Status:** Requirements discovery (2026-07-25). Not yet designed or scheduled.
**Goal:** parkDaddy v3.2.0 live on the Google Play production track, at feature parity with the shipped iOS build.
**Context:** Play developer account already purchased. iOS build 18 shipped via App Store (May 2026). This is the app's first Android release ever.

## 1. Bedrock facts (verified against the repo)

- Expo + EAS project, `appVersionSource: local`, production profile has `autoIncrement: true` — the stale `versionCode: 2` in app.json bumps automatically at build time. No manual bump needed.
- `eas.json` has no Android submit config (commented out). This is fine for launch: **Google requires the first AAB to be uploaded manually through the Play Console UI**; `eas submit` automation (service account JSON) only becomes useful for release 2+.
- Package name `com.parkdaddy.app`; Play App Signing + EAS-managed upload keystore is the default path — no keystore work needed beyond letting EAS generate one.
- The `android/` folder is gitignored and regenerated by prebuild/EAS from `app.json`; nothing in it is source of truth. Its manifest was regenerated 2026-05-21 and already contains the `parkdaddy` scheme intent filter. `POST_NOTIFICATIONS` still needs verifying in the generated manifest before trusting notifications on Android 13+. (Corrected 2026-09-16; earlier claim of a stale 2026-04-12 folder was wrong.)
- No location APIs anywhere (no expo-location / task-manager; no location permissions). Data collected: account identity via Clerk (email, name, Google SSO), crash/diagnostics via Sentry (device identifiers), parking-session app data via Convex, push tokens via expo-notifications.
- `expo-apple-authentication` is in the dependency tree — Apple sign-in either needs to work on Android (it won't natively) or be hidden on the Android build.
- Google Play listing copy (short + full description) already written in `docs/store-listing.md` — only graphic assets remain for the listing.

## 2. Functional requirements

- **FR-1 App runs on Android.** Production-profile build installs and completes a full smoke test on a physical Android device: cold start, splash sequence, sign-up, sign-in, create/end a parking session in both Daily and Extended Stay modes.
- ~~**FR-2 Google SSO works on Android.** Requires an Android OAuth client in Google Cloud (package name + SHA-1 of the Play App Signing key) wired into Clerk. Currently only the iOS URL scheme exists in config — assume unconfigured until proven otherwise.~~ Struck 2026-09-16: Google SSO works on Android with no Android OAuth client because Clerk's `oauth_google` strategy is web-based. See `android-device-defects-requirements.md`.
- **FR-3 Auth-method parity decision honored.** Apple sign-in button must not appear (or must gracefully no-op) on Android.
- **FR-4 Notifications work on Android 13+.** Runtime `POST_NOTIFICATIONS` prompt appears, expiry/check-in notifications deliver, notification channel + icon/color render correctly.
- **FR-5 Splash parity.** The two-stage animated splash behaves on Android as shipped on iOS (native splash → animated stage, correct `#0f172a` background).
- **FR-6 Biometric sign-in** (expo-local-authentication) works with fingerprint/face unlock on Android or degrades gracefully.

## 3. Store & compliance requirements

- **SR-1 Play Console app created** under the purchased account; identity verification completed.
- **SR-2 Closed-test gate (CONDITIONAL — biggest schedule risk).** Personal developer accounts created after Nov 2023 must run a closed test with a minimum tester count (currently ~12) opted in for **14 continuous days**, then apply for production access. Organization accounts are exempt. Verify which applies in the Play Console.
- **SR-3 Store listing assets:** 512×512 icon, 1024×500 feature graphic, ≥2 Android phone screenshots (iOS-framed screenshots are not acceptable). Descriptions already exist in `docs/store-listing.md`.
- **SR-4 Privacy policy URL** publicly reachable (likely exists from the App Store submission — confirm and reuse).
- **SR-5 Data safety form** declaring: email/name (account management, via Clerk), device/crash identifiers (analytics/diagnostics, via Sentry), app activity (parking sessions, via Convex), push tokens. No location, no data sold.
- **SR-6 Content rating questionnaire** completed (expect "Everyone").
- **SR-7 Target audience & content declarations** (18+ / not child-directed), ads declaration (none).

## 4. Non-functional requirements

- **NFR-1** Target API level meets Google's current requirement (Expo SDK default should satisfy; verify at build).
- **NFR-2** AAB (not APK) for the store; builds via `eas build -p android --profile production`.
- **NFR-3** Sentry receives events from the Android build (release + dist tagged).
- **NFR-4** No regression to iOS: shared-code changes for Android (e.g. hiding Apple sign-in) must not alter iOS behavior. Never break userspace.

## 5. Acceptance criteria

1. Fresh production AAB built by EAS from `main`, versionCode ≥ 3 auto-assigned.
2. Full smoke test (FR-1..FR-6) passes on at least one physical Android device, Android 13+.
3. Play Console listing 100% complete (no outstanding warnings on the dashboard).
4. If closed-test gate applies: 14-day/~12-tester requirement satisfied and production access granted.
5. Release rolled out to production and status "Available on Google Play"; install from the store succeeds on a clean device.
6. Memory `project_status` updated with the live date.

## 6. Phased plan (sequencing only — design/details per phase later)

- **Phase 0 — Console setup & gate discovery:** create app in Play Console, complete verifications, determine SR-2 applicability. (Determines the entire timeline; do first.)
- **Phase 1 — Android runtime verification:** regenerate/verify `android/`, build a preview APK, smoke test on device, fix what breaks (FR-1..6).
  - Device smoke-test defects (icon, SSO callback) tracked in `android-device-defects-requirements.md` / `android-device-defects-design.md`.
- **Phase 2 — Listing & compliance:** assets, privacy policy, data safety, content rating (SR-3..7). Parallelizable with Phase 1.
- **Phase 3 — Closed testing:** upload first AAB manually to the closed track, recruit testers, ride out the 14 days if required (else a short internal-testing sanity pass).
- **Phase 4 — Production:** apply for/confirm production access, promote release, staged rollout, monitor Sentry + Play vitals.

## 7. Decisions (answered 2026-07-25)

1. **Account type: ORGANIZATION** (corrected 2026-09-16). The closed-test gate (SR-2) does not apply.
2. **Test device: user owns an Android device.** Phase 1 smoke tests run on it via internal-distribution APK.
3. **Android auth: Google SSO only.** Hide the Apple sign-in button on Android (platform check); no email/password fallback.
4. **Tester recruitment: not required** (see §8).
